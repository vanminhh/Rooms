### Routes, trạng thái và props

- Public layout: `/phong` → `PublicRoomsPage`, `/toa/:id` → `PublicBuildingPage`, `/phong/:id` → `PublicRoomPage`. Staff layout: `/ql/toa-nha` → `BuildingsPage`, `/ql/toa-nha/:id` → `BuildingDetailPage`, `/ql/nhan-su` → `ManagersPage` (bọc `RequireAuth allow={['BOSS']}`), `/ql/phong` → `RoomsPage`, `/ql/don-gia` → `PricesPage`, `/ql/duyet-gia` → `ApprovalsPage` (Boss), `/ql/lich-hen` → `ViewingsPage`. Các trang placeholder có heading riêng và “Đang làm”; giữ route auth/account/home cũ. Guard của `/ql/nhan-su`, `/ql/duyet-gia` phải chặn URL trực tiếp của manager, không chỉ ẩn menu (`AUTH-06`, `UI-08`).
- `BuildingSelection = number | 'all' | null`. `number` = một tòa cụ thể; `'all'` = Boss chọn “Tất cả tòa” (Boss luôn resolve về `'all'`, không bao giờ `null`); `null` = manager chưa chọn tòa (có 0 hoặc từ 2 tòa trở lên). Provider trong `StaffLayout` cho `selectedBuildingId`, `setSelectedBuildingId`; lưu `sessionStorage`, đối chiếu lại `user.buildings` sau refresh/đổi tài khoản, manager chỉ nhận ID trong scope. Query key chứa giá trị `BuildingSelection` và `includeInactive` khi có.
- **Quy tắc truy vấn (áp dụng cho mọi nơi gọi API danh sách/chi tiết có lọc tòa — CP-4, CP-5, CP-7 và bất kỳ chỗ khác):** `number` → gửi `buildingId=<id>`; `'all'` và `null` → **không** gửi tham số `buildingId`. Khi `null`, manager vẫn tải danh sách bình thường, BE trả mọi tòa trong phạm vi quyền (`SCOPE-02`); placeholder “Chọn tòa” chỉ là hiển thị, không chặn tải và không phải trạng thái empty. Khi tài khoản không được giao tòa nào, selector hiện “Chưa được giao tòa nào” (disabled) và danh sách hiển thị empty theo dữ liệu BE trả về.
- Menu Boss có Việc hôm nay, Tòa nhà, Nhân sự, Phòng, Đơn giá, Duyệt giá, Lịch hẹn, Tài khoản; manager bỏ Nhân sự và Duyệt giá.
- `roomStatusLabels: Record<'Đang thuê'|'Đã cọc'|'Bảo trì'|'Trống', {label:string,tone:StatusTone}>`; `viewingStatusLabels: Record<'NEW'|'CONFIRMED'|'WON'|'LOST'|'CANCELLED',string>`; `approvalStatusLabels: Record<'PENDING'|'APPROVED'|'REJECTED'|'SUPERSEDED',string>` và nhãn derived `expired: 'Quá hạn'`. Không tính lại status phòng từ contract (`G-08`); dùng `status` BE. `StatusTone` dùng 4 tone của `StatusBadge`.
- `ConfirmDialogProps = {open:boolean; title:string; description:ReactNode; confirmLabel:string; cancelLabel?:string; pending?:boolean; onConfirm():void; onClose():void}`; khóa focus, Escape/đóng trả focus, action là `<button>`. `ImageUploaderProps = {images:{id:number;url:string;alt:string}[]; maxImages:number; maxBytes:number; accept:string; onUpload(file:File):Promise<void>; onDelete(id:number):Promise<void>; onReorder?(ids:number[]):Promise<void>}`. Kit không import type feature hay gọi API; feature truyền giới hạn/callback (`KIT-03/07`, `ROOM-07`). `ListState` mọi danh sách: loading, empty kèm bước tiếp, error + retry, data (`UI-03`). Form dùng react-hook-form + zod; `applyApiError` map `error.fields` và hiện `error.message` (`UI-05/09`).

### API, DTO và lỗi

Tất cả route dưới `/api/v1`; `apiRequest<T>(path, options)` hiện trả `data`. Bổ sung `apiRequestPage<T>(path):Promise<{data:T[];meta:{page:number;limit:number;total:number}}>` dùng chung cơ chế Bearer/refresh/error của `apiRequest`, không coi danh sách là một mảng đơn lẻ. `GET` mặc định `page=1&limit=20`, `limit` tối đa 100. Query dùng `URLSearchParams`, không nối raw input. Trang có điều khiển phân trang; không cắt mất tòa/phòng/nhân sự ngoài trang đầu.

| Hợp đồng | Request/query → response `data` | Lỗi cần hiện |
|---|---|---|
| `GET /buildings` | `buildingId?,includeInactive?,page,limit,sort?` → `BuildingView[]` + `meta`; `BuildingView={id,code,name,address,district,ward,waterMode:'PER_M3'|'PER_PERSON',dueDays,managerId,manager:{id,fullName,isActive}|null,amenities:string[],description:string|null,isActive,pendingViewingCount,createdAt,updatedAt}` | `OUT_OF_SCOPE` 403; `FORBIDDEN` 403 manager + includeInactive |
| `POST /buildings`, `PATCH /buildings/:id` | `CreateBuilding={code,name,address,district,ward,waterMode,dueDays?,managerId?:number|null,amenities?,description?}`; patch partial + `isActive?`; → `BuildingView`. Manager patch chỉ `amenities`, `description`. | `VALIDATION_FAILED` 400 (`fields`), `MANAGER_MAX_2_BUILDINGS` 409, `CONFLICT_STATE` 409 khi khóa có HOLD/ACTIVE |
| `GET /services`, `POST /services`, `PATCH /services/:id` | Query `buildingId?,page,limit,sort?`; `ServiceView={id,buildingId,name,unit:'ROOM'|'PERSON'|'VEHICLE',isActive,hasCurrentRate}`. Create `{buildingId,name,unit}`; patch `{name?,isActive?}`. | `FORBIDDEN` 403 manager mutating, `OUT_OF_SCOPE` 403, `VALIDATION_FAILED` 400 duplicate/invalid |
| `GET /managers`, `POST /managers`, `PATCH /managers/:id` | Boss only. Query `buildingId?,page,limit,sort?`; `ManagerView={id,phone,fullName,email,isActive,mustChangePassword,contactPhone,zaloUrl,facebookUrl,buildings:{id,code,name,isActive}[],createdAt}`. Create `{phone,fullName,email?}` → `{manager:ManagerView,temporaryPassword:string}`; patch `{isActive:boolean}` → `ManagerView`. | `PHONE_TAKEN` 409, `VALIDATION_FAILED` 400, `FORBIDDEN` 403 |
| `GET /rooms`, `POST /rooms`, `PATCH /rooms/:id` | Query `buildingId?,includeInactive?,page,limit,sort?`; list `RoomGridItem[]` + `meta`. `RoomView={id,buildingId,code,floor,areaM2,price:number|null,maxOccupants,furniture:string[],description:string|null,underMaintenance,isActive,status,images:RoomImageView[],pendingViewingCount?}`. `RoomGridItem` bỏ furniture/description/images, thêm `pendingProposal:{id,effectiveFrom:'YYYY-MM-DD',expired}|null,imageCount`. Create `{buildingId,code,floor,areaM2,maxOccupants?,furniture?,description?}`; patch partial trừ `buildingId`, thêm `underMaintenance?,isActive?`. `price` không bao giờ gửi. | `VALIDATION_FAILED` 400 (mã trùng kể cả khóa), `OUT_OF_SCOPE` 403, `CONFLICT_STATE` 409: khóa/bảo trì có hợp đồng, giảm sức chứa dưới số người hiện tại, tạo trong tòa khóa |
| `GET /rooms/:id` **(chờ backend)** | `:id` → `RoomView` đầy đủ, luôn có `images:RoomImageView[]` và `pendingViewingCount:number` (số lịch `NEW/CONFIRMED`). FE gọi trước khi mở dialog khóa/bảo trì và sau refresh để dựng lại gallery. | `OUT_OF_SCOPE` 403, `NOT_FOUND` 404 |
| `POST /files/sign` | `{purpose:'ROOM_IMAGE',roomId}` → `SignedUpload={cloudName,apiKey,uploadUrl,timestamp,folder,allowedFormats,transformation,signature}` | `UPLOAD_NOT_CONFIGURED` 503 “Chưa cấu hình tải ảnh”; `OUT_OF_SCOPE` 403 |
| Cloudinary `POST uploadUrl` | `FormData` chứa file và đúng `api_key,timestamp,folder,allowed_formats,transformation,signature` từ BE → `{asset_id,public_id,version,format}`. Không gửi bearer/refresh cookie sang Cloudinary. | Upload lỗi: thông báo tiếng Việt, không attach |
| `POST /rooms/:id/images`, `PATCH /rooms/:id/images/order`, `DELETE /rooms/:id/images/:imageId` | Attach `{assetId,publicId,version,format}` → `RoomImageView={id,roomId,publicId,url,sortOrder}`; order `{imageIds:number[]}` → `RoomImageView[]`; delete → `null`. | `VALIDATION_FAILED` 400 metadata/folder, `CONFLICT_STATE` 409 >10 ảnh, `UPLOAD_NOT_CONFIGURED` 503, `OUT_OF_SCOPE` 403 |

BE là nơi kiểm quyền, giao dịch, tính tiền và xác minh Cloudinary. FE không gửi URL ảnh hoặc `assetId` vào query/log; `RoomImageView.url` là URL BE tạo chỉ để hiển thị. Khi mutation thành công, invalidate query liên quan của tòa, dịch vụ, nhân sự, phòng/ảnh. 409 hiển thị `error.message`, refetch state rồi cho người dùng thử lại; không tự ghi đè. `pendingViewingCount` là số `NEW/CONFIRMED` từ BE: dialog trước khi khóa tòa, khóa/bảo trì phòng phải ghi “Còn N lịch hẹn chưa xử lý”; thành công thì refetch, không tự hủy lịch. `BuildingView` đã có count; `RoomGridItem` không mang count, nên số lịch trước xác nhận và danh sách ảnh sau refresh đều lấy từ `GET /rooms/:id` (quyết định chủ dự án 04/11/2026). Endpoint này **chưa có ở backend**: FE khai báo một hàm API mỏng `getRoom(id)` đúng hợp đồng trên, test bằng mock/fixture; chỉ khi backend draft riêng được duyệt và áp dụng thì mới kiểm với API thật. Form tòa Boss code 2–6 `A-Z0-9`, `dueDays` 1..31; form phòng `floor`/`maxOccupants` nguyên ≥1, `areaM2` >0 và ≤9999.9, một chữ số thập phân; ảnh tối đa 10, mỗi ảnh ≤ `5_000_000` byte (chặn trước khi gọi `/files/sign`), chỉ JPG/PNG/WebP. Tiền `price` chỉ hiển thị số nguyên bằng `formatMoney`; `null` → “Chưa có giá”. Ngày từ API hiển thị `dd/mm/yyyy` từ chuỗi `YYYY-MM-DD` theo Hà Nội, không diễn giải bằng UTC để lùi ngày cuối tháng.

DB liên quan chỉ đọc qua BE, không sửa schema: `buildings(id,code,name,address,district,ward,manager_id,water_mode,due_days,amenities,description,is_active)`, `users(id,phone,full_name,email,role,is_active)`, `rooms(id,building_id,code,floor,area_m2,price,max_occupants,furniture,description,under_maintenance,is_active)`, `room_images(id,room_id,asset_id,public_id,url,sort_order)`, `services(id,building_id,name,unit,is_active)`, `viewings(id,room_id,status)`, `contracts(id,room_id,status)`. Phòng và tòa khóa bằng `is_active=false`; không xóa lịch sử.

## 3. Quyết định của chủ dự án, phần chờ backend, giả định

**Câu hỏi bỏ ngỏ: không có.** Chủ dự án đã trả lời ngày 04/11/2026 (ghi trong feature file), đây là luật nghiệp vụ, không phải `[ASSUMPTION]`:

- **Q-FE8A-1 → A (`ROOM-07`):** ngưỡng ảnh FE là `5_000_000` byte. FE từ chối file `> 5_000_000` byte trước khi gọi `/files/sign`. Tester kiểm `5_000_000` (nhận) và `5_000_001` (chặn).
- **Q-FE8A-2 → B và Q-FE8A-3 → A (`ROOM-09`/`VIEW-13`, `ROOM-07`):** một endpoint duy nhất `GET /rooms/:id` trả `RoomView` có cả `pendingViewingCount` (lịch `NEW/CONFIRMED`) và `images`. FE gọi nó trước khi mở dialog khóa/bảo trì phòng và sau refresh để dựng gallery; không giả số 0, không lấy count sau thao tác để hiện trước.
- **Q-FE8A-4 → “Gọi API không kèm tòa” (`FE-P2-03`, `SCOPE-02`):** manager có 2 tòa và chưa chọn tòa (`BuildingSelection = null`) thì FE vẫn gọi API danh sách **không kèm** `buildingId`, hiện dữ liệu mọi tòa được giao; BE tự giới hạn theo quyền. Boss chọn “Tất cả tòa” (`'all'`) cũng không gửi `buildingId`. Có thể lọc theo tòa sau khi người dùng chọn.
- **Phần chờ backend:** `GET /rooms/:id` chưa tồn tại; backend sẽ làm trong một draft riêng. FE vẫn hiện thực đủ theo hợp đồng ở mục 2 qua `getRoom(id)` trong `src/features/rooms/api.ts`, và tester kiểm bằng mock `fetch`/fixture. Ảnh hưởng: phần dialog của **CP-7** và toàn bộ **CP-8** chỉ PASS ở mức draft/mock; kiểm với API thật (gate `FE-P2-08` trên main) chỉ chạy được sau khi backend endpoint được duyệt và áp dụng. CP-1..CP-6 không phụ thuộc endpoint này và chạy bình thường.
- Luồng ảnh gửi đủ 4 field `assetId`, `publicId`, `version`, `format` theo `UI-10`/`FILE-02`; không gửi URL hiển thị.
- `[OPEN] Q-01` thuê chồng thời gian, Q-02 bảng giá điện thật, Q-03 webhook trong `00-overview` nằm ngoài phạm vi; không đưa giá seed hay quyết định mới vào FE.
- `[ASSUMPTION] A-07` của spec (cookie phiên 12 giờ) là BE/auth hiện có, FE chỉ giữ lựa chọn tòa trong `sessionStorage`. `[ASSUMPTION]` ở BE về lời nhắn lỗi không được FE sao chép thành luật; hiển thị `error.message`. Không tạo giả định nghiệp vụ mới.
- Quy ước kỹ thuật có thể đổi trong coder mà không đổi nghiệp vụ: chọn tòa đầu tiên thuộc scope nếu manager có đúng một tòa; với 0 hoặc từ 2 tòa, giá trị khởi tạo là `null` để người dùng chọn, Boss mặc định `'all'` (“Tất cả tòa”). ## 4. Checkpoints theo thứ tự phụ thuộc

### Quyết định kỹ thuật CP-3 (planner, 04/11/2026 — không phải luật nghiệp vụ, không cần hỏi chủ)

- **Q1 — khi `pending`, Escape và nút Hủy vẫn đóng dialog: giữ nguyên, không đổi code.** PLAN mục 2 chỉ yêu cầu “khóa focus, Escape/đóng trả focus” và tester chỉ kiểm “confirm một lần”; `KIT-05`/`UI-08` buộc bàn phím luôn hoạt động, nên chặn Escape khi đang chờ sẽ khóa người dùng lại nếu request treo. `aria-disabled` trên nút xác nhận đã bảo đảm “confirm một lần”. Bên gọi (feature) chịu trách nhiệm: đóng sớm chỉ ẩn dialog, mutation vẫn chạy tới cùng và `invalidate` theo mục 2 nên state không sai. `[ASSUMPTION] A-CP3-1`: dialog không khóa đường đóng khi `pending`; nếu sau này chủ dự án muốn chặn (ví dụ thao tác tiền theo `UI-04`), thêm cờ riêng, không đổi hành vi mặc định.
- **Q2 — xóa ảnh không có hộp xác nhận: đúng spec, giữ nguyên code.** `UI-04` chỉ bắt buộc hộp xác nhận cho **thao tác tiền** (thu tay, phát hành lại, gán giao dịch, tất toán, duyệt giá); `ROOM-07`/`FILE-01/02` và `KIT-03/07` không yêu cầu xác nhận khi xóa ảnh phòng. Ảnh cũng không phải dữ liệu lịch sử bị cấm xóa cứng (chỉ `is_active` áp cho tòa/phòng). `ImageUploader` vẫn chỉ nhận `onDelete(id)` và không tự hỏi.
- **Q3 — `src/components/README.md` không thuộc CP-3.** Nó không có trong bảng file mục 2 và `KIT-07` chỉ đòi token `rooms.css`, export `index.ts`, mẫu trong preview và test khi có logic — README không nằm trong danh sách đó. Đây là **việc sau khi duyệt**: main session cập nhật props map của `ConfirmDialog`/`ImageUploader` trong một draft riêng (mirror `src/components/README.md`) rồi apply. Coder **không** tạo hay sửa README trong nháp này.

### Quyết định kỹ thuật CP-4 (planner, 04/11/2026 — kỹ thuật trong phạm vi nháp, không phải luật nghiệp vụ)

- **Q1 — `listPath` giữ `RangeError` cho `page`/`limit` sai: giữ nguyên, không đổi code.** `page`/`limit` không phải input người dùng mà do điều khiển phân trang của FE sinh ra, nên lỗi ở đây là lỗi lập trình, chặn sớm một dòng còn rẻ hơn một vòng network trả 400. Biên giới tin cậy thật vẫn ở BE (`API-02/04`): FE không được coi kiểm này là thay thế. Lưu ý cho coder CP-5..CP-8: chỉ truyền số nguyên từ state phân trang, không truyền chuỗi thô từ URL/ô nhập; nếu sau này đọc `page` từ query string thì parse và kẹp (clamp) tại trang, không dựa vào throw. Tester CP-4 kiểm cả hai mặt: `page=1/limit=20/limit=100` hợp lệ, `0`, `1.5`, `101` ném `RangeError`, và 400 `VALIDATION_FAILED` từ BE vẫn hiện `error.message`.
- **Q2 — schema mã tòa nhận chữ thường: đúng, giữ nguyên `/^[A-Za-z0-9]{2,6}$/`.** `BLD-06` nói rõ “the BE upper-cases input”, và `CreateBuildingDto` có `@Transform(value.toUpperCase())` trước `@Matches`, nên chữ thường là input hợp lệ của hợp đồng. FE không tự chuẩn hóa thành chữ in để tránh hai nguồn sự thật; `BuildingView.code` hiển thị luôn là giá trị BE trả về (đã in hoa). Nếu CP-5 muốn người dùng thấy ngay chữ in thì chỉ dùng `text-transform: uppercase` ở CSS của input, không đổi giá trị form.
- **Q3 — mâu thuẫn CP-4/CP-8 về `getRoom`: PLAN đã sửa.** Dòng CP-8 trong bảng checkpoint nay ghi “dùng `getRoom(id)` đã có từ CP-4”; CP-8 không khai lại hàm này.
- **Q4 — vị trí API ảnh.** `src/features/rooms/upload.ts`: `signUpload(roomId): Promise<SignedUpload>` (gọi `POST /files/sign` qua `apiRequest`) và `uploadToCloudinary(signed, file): Promise<{assetId,publicId,version,format}>` (gọi `fetch` trực tiếp bằng `FormData`, **không** dùng `apiRequest` để không gửi Bearer/cookie sang Cloudinary, và kiểm `5_000_000` byte + MIME JPG/PNG/WebP trước khi sign). Ba endpoint của ta nằm trong `src/features/rooms/api.ts` cùng chỗ với `getRoom`/`listRooms`: `attachRoomImage(roomId,{assetId,publicId,version,format})`, `reorderRoomImages(roomId, imageIds)`, `deleteRoomImage(roomId, imageId)`. Lý do: convention `features/<module>/api.ts` = API của ta, còn `upload.ts` là riêng luồng ký + nhà cung cấp ngoài. Không tạo `features/files/`.
- **Q5 — trang chi tiết tòa (CP-5) dùng `listBuildings`, không chờ backend.** Bảng API của `docs/spec/11-buildings-rooms.md` chỉ có `GET/POST/PATCH /buildings` (không có `GET /buildings/:id`; `/public/buildings/:id` là trang công khai, ngoài phạm vi 8a) và backend controller cũng chỉ có `@Get()`, `@Post()`, `@Patch(':id')`. Vậy `BuildingDetailPage` gọi `listBuildings({ buildingId: id, limit: 1, includeInactive: user.role === 'BOSS' })` rồi lấy `data[0]`; `data` rỗng → state “Không tìm thấy tòa nhà” (không giả 404 của BE). `includeInactive` chỉ gửi khi Boss vì manager + `includeInactive` bị 403 `FORBIDDEN` theo hợp đồng mục 2. Không mở yêu cầu backend mới.
- **Q6 — `getRoom` giữ `pendingViewingCount: number` bắt buộc.** `RoomView.pendingViewingCount` optional vì `POST`/`PATCH /rooms` không bắt buộc trả nó, còn hợp đồng `GET /rooms/:id` ở mục 2 (quyết định chủ dự án Q-FE8A-2) nói “luôn có”. Kiểu hiện tại `apiRequest<RoomView & { pendingViewingCount: number }>` thể hiện đúng cả hai, nên không đổi code; dialog khóa/bảo trì không được dùng `?? 0`.
- **Q7 — `src/shared/formatters.ts` thuộc CP-4.** Đã thêm vào bảng file mục 2 và cột file CP-4: `formatDate` là điều kiện của `G-02` và `UI-01` ngay từ CP-5 (`effectiveFrom`, `createdAt`), và file này đã có trên main nên draft chỉ thêm hàm, giữ nguyên `formatMoney`. Không chuyển sang checkpoint khác.

Kết quả test phải ghi lệnh, exit code, số test và phạm vi thực; preview không tự chứng minh phiên đăng nhập/BE thật nếu chỉ dùng fixture. `FE-P2-08` trên main chỉ hoàn tất khi main session đã áp dụng draft theo owner approval, chạy lại 3 lệnh app, rồi Boss và manager tạo tòa/phòng trên browser với API thật; phần ảnh và dialog lịch hẹn của gate này cần `GET /rooms/:id` đã có trên backend.
